## 6. Prefilter ordering and recomputability

There is **no insert-then-classify pattern in the sweep**.

1. 8004scan list rows have the small named shape at
   [`discoveryPipeline.ts:131`](../convex/discoveryPipeline.ts#L131).
2. The sweep maps the in-memory rows through `evaluateCheaply` at
   [`:457`](../convex/discoveryPipeline.ts#L457).
3. `evaluateCheaply` calls `prefilterAgent(name, description)` and returns a
   rejected verdict before `scoreAgent` at [`:251`](../convex/discoveryPipeline.ts#L251).
4. Already-judged records are dispatched at [`:487`](../convex/discoveryPipeline.ts#L487).
5. `recordSweepBatch` inserts the row with its final cheap verdict at
   [`:869`](../convex/discoveryPipeline.ts#L869).

The insertion is unconditional on status. The pipeline knows a row is spam in
memory, then persists a full-width rejection receipt anyway.

`prefilterAgent` is string work over compile-time constants and performs no I/O
([`prefilter.ts:151`](../convex/lib/prefilter.ts#L151)). The current candidate
sweep imports this function from `prefilter.ts`, **not** from
`classification.ts`; `classification.ts` belongs to the older discovery path.

The precise recomputability claim is:

> Given the same `(name, description)` list record and the same deployed
> prefilter code, the verdict can be recomputed during an existing sweep with
> no additional network call.

Token ID alone is not enough. Upstream text can change, a later code version can
change constants, and the sweep is currently disabled. A tombstone that stores
neither the historical text nor a rule/version marker cannot reproduce the old
verdict exactly.

The separate submission path really does insert a blank pending row and hydrate
it later ([`agentSubmissions.ts:130`](../convex/agentSubmissions.ts#L130),
[`agentSubmissions.ts:240`](../convex/agentSubmissions.ts#L240)). It is
user-triggered and not the source of the bulk storage problem.

`by_agent` is not a prefix of `by_token`, and `by_token` is not a prefix of
`by_agent`: their second columns are `registryAddress` and `tokenId`
respectively. Convex's ordered-prefix behavior therefore provides no free drop.
See the official [index documentation](https://docs.convex.dev/database/reading-data/indexes/).

The transcript sampled 2,000 prefilter rejects and saw one registry address.
That makes `by_agent` a promising narrowing target, but it does **not** prove a
global invariant. Submissions accept an arbitrary syntactically valid contract
address ([`agentSubmissions.ts:97`](../convex/agentSubmissions.ts#L97)), and the
schema explicitly allows token-ID collisions across registries
([`schema.ts:206`](../convex/schema.ts#L206)). The report's “≤2 rows per token”
and “nothing breaks after three call-site changes” claims are not established.

Likewise, the projected **230–280 MB** recovery from dropping `by_agent` is an
estimate, not a measured result. Do not change call sites or schema until an
authorized task proves global registry/token cardinality and defines the
collision-preserving replacement behavior.

## 8. The bounded delete instrument

The second task explicitly authorized deleting at most 5,000 oldest
`rejected-prefilter` rows in ten 500-row batches. The runner reported:

```text
selected JSON bytes       6,140,991
deleted JSON bytes        6,140,991
mutation deleted count        5,000
skipped                           0
script's JSON-byte I/O model 18,422,973 B
```

The saved IDs are in
[`docs/purge-instrument-2026-09-02-deleted-token-ids.txt`](purge-instrument-2026-09-02-deleted-token-ids.txt):
5,000 token-ID lines plus three comment/summary lines.

Two caveats are load-bearing:

1. **Those IDs do not prove exact document identity or full recoverability.**
   Selection saved only `tokenId` ([`zz_diagRowSize.ts:257`](../convex/zz_diagRowSize.ts#L257));
   deletion looked up `(chainId, tokenId)` and took `.first()` without
   `registryAddress` ([`:288`](../convex/zz_diagRowSize.ts#L288)). Cross-registry
   collisions are allowed. The mutation proves it deleted 5,000 documents that
   were `rejected-prefilter` at deletion time; it does not prove each physical
   document was the exact one selected oldest-first.
2. **18.4 MB is not billed Convex Database I/O.** It is the runner's model:
   selected JSON bytes + lookup JSON bytes + assumed write JSON bytes. It omits
   Convex encoding and index maintenance. The transcript's ~927 MB two-pass and
   ~617 MB single-pass full-purge projections are floors derived from that
   model, not safe budget figures.

The transcript did not capture the dashboard storage figure immediately before
or after deletion. The deleted documents total only ~6.14 MB of sampled JSON,
or roughly ~18 MB after applying the inferred multiplier. A dashboard rounded
to 0.01 GB may show no movement even if reclamation is immediate. Therefore a
flat displayed value is **inconclusive**, not evidence of delayed compaction.

Official Convex docs explain how to delete documents and what storage includes,
but the checked pages do not state when deleted-document storage disappears
from billing/usage:

- [Writing data](https://docs.convex.dev/database/writing-data)
- [Database limits and usage](https://docs.convex.dev/production/state/limits)
- [Dashboard data controls](https://docs.convex.dev/dashboard/deployments/data)

Storage reclamation remains **NOT PROVEN**. A timestamped dashboard observation
or an answer from Convex support is still needed.
