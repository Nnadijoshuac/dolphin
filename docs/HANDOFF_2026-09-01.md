## 2. EVERY FINDING — INCLUDING THE ONE THAT WAS WRONG

### 2a. The retraction, and the lesson that generalises

**I published a confident, wrong conclusion mid-session and had to retract it.**
It is the most useful thing in this document, because a future agent will hit
the same class of error.

I reported that `useaiki.xyz` **did not exist**, that four agents advertising it
were correctly marked `unreachable`, and that delisting token `315943` was the
right outcome. Evidence cited: NXDOMAIN from the local resolver, Google
`8.8.8.8`, Cloudflare `1.1.1.1`, and Cloudflare DoH returning `Status: 3` with
an SOA from `ns0.centralnic.net` — the `.xyz` registry's own nameserver.

**Re-tested ~45 minutes later: the domain resolved from all five vantage
points.** `agentcensus.xyz` flipped identically. Nobody did anything in between.

> **The lesson: multiple public resolvers are NOT independent witnesses.** They
> all ultimately consult the same registry nameservers, so a registry-level
> fault produces an identical NXDOMAIN everywhere at once. Agreement across
> resolvers measures *consistency*, not *correctness*. **A negative network
> result must be re-tested across time before it is written up as a property of
> the world rather than of the moment.**

I compounded it by citing a `useaiki.ai` "Coming Soon" page as corroboration.
That is a *different domain* that merely shares a stem. It proved nothing.

Both observations are preserved with timestamps in `docs/PROBE_DIAGNOSIS.md` —
correction on top, original beneath, unedited.

### 2c. Two real probe defects, both now fixed

**Fix 1 — templated URLs** (commit `c0194fb`). Every TermiX-hosted agent
advertises `…/api/v1/a2a/agents/{agentId}/card`. We fetched that literally,
got 404, and incremented `consecutiveProbeFailures` toward delisting for a
request that could never succeed. The payment path already guarded against this
([convex/lib/erc8183.ts:319](../convex/lib/erc8183.ts#L319)); the probe did not.

```

```

**Fix 2 — protocol dispatch** (commit `09eedf4`). ERC-8004 does **not** define a
service's `name` as a protocol identifier — checked against the spec, which
lists `web`, `A2A`, `MCP`, `OASF`, `ENS`, `DID`, `email` side by side, says
"The number and type of endpoints are fully customizable", makes `version` "a
SHOULD, not a MUST", and gives **no guidance at all** on determining an
endpoint's protocol. `probeLiveness` had two branches and treated every label
without `mcp` as A2A. Four live agents were failed for not speaking a protocol
they never advertised.

```

verified-live 16 -> 20
unreachable   36 -> 32
```

### 2e. A false positive the control set caught

Fix 2's first run marked token `325413` live via an `oasf` endpoint pointing at
`https://github.com/agntcy/oasf`. **GitHub content-negotiates**: sent

again.

> **Generalise this: always run a new liveness rule against a control set of
> things it must REJECT, not only the things you want it to admit.**

## 3. THE THREE THINGS THAT ARE *NOT* THE BOTTLENECK

Do not re-investigate these. Each was measured this session.

**① Fetch throughput is not the bottleneck.** The new 8004scan key measures
**3,000 req/min and 3,000,000/day**. `offset` pagination works (undocumented),
`chain_id` is a real filter, and concurrency 32 was served with zero rejections
at 537 records/s. **A full walk of the ~297,000 chain-56 registry takes ~7
minutes and 0.1% of daily quota.** Full working: `docs/INGESTION_AUDIT_2.md`.

**② Registry coverage is not the bottleneck.** 73%+ of the registry was already
evaluated before this session. Every high-value agent found by searching the
catalog's own vocabulary — RangeKeeper, Aave-HeyAnon, Venus-HeyAnon,
V3Pools-HeyAnon — had **already been fetched, cross-checked and probed**. They
were absent for classifier reasons, not coverage reasons.

**③ The classifier threshold is not the bottleneck.** `CONFIRMED_SCORE = 12`,
`CONFIRMED_MARGIN = 6`, `LIKELY_SCORE = 4`
([convex/lib/agentScoring.ts:229-231](../convex/lib/agentScoring.ts#L229)). The
spam it rejects — BORT collectibles, "Autonomous trading agent (simple-mode)"
campaigns, EvoEvo personas — is correctly rejected. Lowering the thresholds
would admit spam, not agents.

### What the actual constraints are

1. **Liveness.** Of everything surviving classification, the large majority
   fails the endpoint probe. That is where the catalog is gated.
2. **Publisher-side defects.** Templated URLs, dead hosts, endpoints pointing at
   spec pages. Nothing we can fix from here.
3. **Classifier *vocabulary*** (not thresholds) — §4b.

## 4. OPEN LEVERS, WITH HONEST SIZE ESTIMATES

### 4a. The 17 null-category verified-live agents — **a manual vouch cannot reach them**

A scan of all `rejected-classifier` rows found **18 that are `verified-live`** —
real, already-probed agents rejected on wording alone. **17 carry
`category: null`.**

`resolveStatus` returns `rejected-classifier` on a null category at
[convex/lib/pipelineStatus.ts:132](../convex/lib/pipelineStatus.ts#L132),
**before** it ever consults `manuallyIncluded` at
[:170](../convex/lib/pipelineStatus.ts#L170). So `setManualOverride` on any of
them is **inert**: the re-queued evaluation re-scores, the classifier returns
`null` again, and they land straight back with the override recorded but unused.

Among them, plainly in-category to a human: `259574` RangeKeeper (*"Moves your
liquidity back into range so it keeps earning"*), `45381` Aave powered by
HeyAnon, `259573` HealthGuard, `269226` Yield Allocator, `304493` Brain on BNB —
Venus Yield Ranking, `293902` mandaterebalance-agent. All scored 0–2 against a
`LIKELY_SCORE` floor of 4.

**Size: up to 6 agents. Requires a classifier change, not a vouch.**

### 4b. The classifier vocabulary gap — **NEVER RUN. Say so.**

A previous task asked for a vocabulary proposal *plus* a full re-score of the
entire ledger to show the diff before applying. **That task was never executed.**
No vocabulary change was proposed, no re-score was run, no diff exists.

The gap is real: the six agents above fail because no *defining* phrase matches.

**Size: unknown until the diff is run. Plausibly 6–15 agents. NOT PROVEN.**

### 4c. Registration-file pricing — identified, unexploited

**Where the price lives.** AiKi's ERC-8004 manifests carry:

```json
"pricing": {"amount": "100000000000000000", "asset": "U"}
```

That is 0.10 $U — **the same token our ERC-8183 escrow settles in**
(`0xcE24439F2D9C6a2289F741120FE202248B666666`), on a live endpoint.

**Why the catalog shows 0 anyway.** Every agent is priced by one constant,
`DEFAULT_READ_ONLY_PRICE_MODEL`
([convex/lib/agentCatalog.ts:147](../convex/lib/agentCatalog.ts#L147)), because
ERC-8004's *on-chain* record has no price field and 8004scan publishes none.
**But the registration file does, and `deepEvaluate` already fetches it** for
the cross-check ([convex/discoveryPipeline.ts:591](../convex/discoveryPipeline.ts#L591)).
The data is already in hand and thrown away.

**Which agents publish one.** Confirmed by reading all four manifests directly:
`315943`, `315944`, `315945`, `315946`. A broader survey of the 20 published
read 14 manifests successfully and found pricing on 1 — **but that survey had
transient fetch failures on three known-positive AiKi manifests, so treat "1 of
14" as a floor, not a measurement.** The honest number is **at least 4 of 20**.
**NOT PROVEN** at catalog scale; a clean re-survey would settle it.

**What would have to change.** `fetchRegistrationFile` would need to parse and
return `pricing`; the candidate row would need a field to hold it; `listAgents`
would need to prefer a real published price over the zero constant.

**What it unblocks.** `hireReadOnlyAgent`'s non-zero-price branch
([convex/agentHires.ts:76-122](../convex/agentHires.ts#L76)) **has never once
fired** — nothing can currently produce a non-zero price to trip it. A real
price would exercise the entire paid-hire path, which is the flagship feature
and is otherwise unexercised. This is the single strongest **Data Quality**
lever in the repo.
